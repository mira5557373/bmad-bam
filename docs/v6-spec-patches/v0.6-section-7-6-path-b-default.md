# v0.6 spec patch — §7.6 Module Activation (Path B as default)

> **Status:** SUPERSEDED by v0.7 (2026-05-13). v0.7 retains Path B as the default but additionally aligns the sentinel-file LOCATION with BMM's `bmad-generate-project-context` convention: `{output_folder}/bam-platform-project-context.md` instead of `_bmad/bam-activation/platform/project-context.md`. v0.7 also abolishes the "survival namespace" concept entirely — BAM's sentinel lives outside `_bmad/` (just like BMM's), so no special survival namespace is needed.
>
> See `docs/v6-final-architecture.md` §7.6 (applied v0.7) and `_bmad/_memory/atlas/architecture-decisions/2026-05-13-005-project-context-location-aligned-to-bmm.md` for the current canonical version. This v0.6 draft is preserved as historical record.

## Context (v0.6, historical)

## Context

The v0.5 spec patch (c) named **Path A (npm postinstall)** as the v6.0 default activation mechanism, on the assumption that BMAD's `bmad install` invokes npm in a way that exposes the host project root.

P2.1 Task 0 (`tests/p2/INVESTIGATION-NOTES.md`) re-evaluated this empirically by reading BMAD 6.6.0's installer source (`external/bmad-method/tools/installer/`). The finding contradicts the v0.5 premise:

1. BMAD runs `npm install --omit=dev` against the cloned community-module repo with `cwd: moduleCacheDir` (e.g., `~/.bmad/cache/community-modules/bmad-bam/`) — **not** the host project (`community-manager.js:396-412`).
2. The `npm install` step is gated on `(needsDependencyInstall || wasNewClone)` — it does NOT fire on every `bmad install`, only on fresh clone / version bump.
3. After install, BMAD's `installFromResolution` copies only the marketplace-declared `skillPaths` into `_bmad/<module-code>/<skill>/` (`official-modules.js:344-376`). Files written by `postinstall` into the repo root (outside skillPaths) are discarded.
4. BMAD has no native code-execution hook. The only "post-install" mechanism is `post-install-notes` in `module.yaml`, which only displays text (`official-modules.js:2103-2143`).

Therefore Path A as defined in v0.5 cannot reliably write `_bmad/<module>/project-context.md` into the host project, and Path C (upstream BMAD hook) does not exist.

This patch proposes the resulting changes to §7.6.

## Proposed replacement for §7.6

Replace the entire current §7.6 ("Module activation in real installs") with the following:

---

### 7.6 Module activation in real installs

**Wave 0 surfaced the gap; P2.1 Task 0 empirically re-evaluated it.** BMAD's installer does not auto-trigger BAM modules' `scripts/post-install.sh`. The universal-glob mechanism (§7.1) requires `_bmad/<module>/project-context.md` to exist; that file is generated by `post-install.sh`; therefore activation in real installs requires triggering the hook out-of-band.

**Three previously-considered activation paths, status after empirical re-evaluation:**

| Path | Mechanism | Status in v0.6 | UX |
|---|---|---|---|
| **A — npm `postinstall`** | `package.json: scripts.postinstall` runs after BMAD's `npm install` against the cached repo | **REJECTED for target-project activation.** npm runs in BMAD's cache directory (`~/.bmad/cache/community-modules/...`), not the host project; only fires on fresh clone or version bump; files written outside `skillPaths` are discarded by the installer copy step. May still be used for harmless cache-dir prep (banner, sanity check on marketplace.json), but cannot reach the host project. | n/a |
| **B — manual finalize step (DEFAULT for v6.0)** | Each BAM module ships a `bmad-bam-finalize` skill the user invokes once after `bmad install <module>`. The user-facing prompt is surfaced via BMAD's native `post-install-notes` channel (`module.yaml: post-install-notes`) | **DEFAULT for v6.0.** One extra user step (~5s); visible in install docs; deterministic across BMAD installer changes; idempotent. | One `bmad run bmad-bam-finalize` after install |
| **C — upstream BMAD hook** | Patch BMAD's installer to consume `x-bam-post-install` (or generic `hooks.post`) from `module.yaml` | **NOT AVAILABLE in BMAD 6.6.0.** No native code-execution hook exists. Could be petitioned upstream long-term but not in BAM's control. | n/a until BMAD ships such a hook |

**Default for v6.0: Path B (manual finalize).** Each BAM module ships:
1. A `bmad-bam-finalize` skill (CEV-style, single step) that invokes `scripts/post-install.sh "$PROJECT_ROOT"` against the host project.
2. A `post-install-notes:` block in `module.yaml` instructing the user to run `bmad run bmad-bam-finalize` after install.

The finalize step is idempotent — safe to re-run; the sentinel file is atomically replaced, the install log is append-only.

**Fallback (Path D, new in v0.6):** if BMAD's installer eventually adds a native post-install code hook (the formerly-Path-C mechanism), BAM modules can migrate by adding the appropriate hook declaration to `module.yaml` and removing the user-facing finalize prompt. Until then, Path B is the only viable mechanism.

**Verification:** P2.1 acceptance includes `tests/p2/run-real-install-test.sh` exercising the Path B finalize flow against a fixture project, plus a manual Plan-C-ratification step (does Claude actually load `project-context.md` at activation time — see `tests/p2/PLAN-C-RATIFICATION.md`). Note: "Plan C" in this verification context is the LLM-side activation contract, distinct from "Path C" the upstream-hook activation mechanism — they are unrelated concepts despite the letter collision.
