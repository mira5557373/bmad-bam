## Context

The bmad-bam-platform module has 16 workflows + 11 cross-family workflows + extensive knowledge architecture (fragments, patterns, gates, standards). P2 as a whole is too large for one plan; needs decomposition into MVP slices that ship usable end-to-end value at each step.

## Decision

P2.1 scope = activation mechanism realization (Path B per ADR 2026-05-12-002) + Atlas full persona overlay + one complete CEV workflow (`design-tenancy-model`) with supporting fragments/patterns/gate + Plan C ratification harness. ~28 tasks executed.

Concretely P2.1 ships:
- `bmad-bam-finalize` skill (Path B activation entry point)
- `bmad-bam-design-tenancy-model` skill (7 steps + template + smoke test)
- 5 fragments under Atlas's resources (tenancy-decision-framework, rls-deep-dive, schema-per-tenant, cell-based-architecture, tenant-isolation-testing-patterns)
- 3 patterns (rls-row-level-security, schema-per-tenant-with-pgbouncer, cell-based-with-routing)
- QG-M2 (Tenant Isolation) checklist
- 3 family-wide standards (std-frontmatter, std-validation, std-adr)
- Atlas sidecar memory templates
- Real-install end-to-end test + Plan C ratification template

## Consequences

- P2.2-P2.5 deliver the remaining 15 platform workflows + 11 cross-family workflows incrementally; each plan should be ~20-30 tasks like P2.1.
- v6.0 ships when all of P2.x complete (plus equivalent slices for the other 7 BAM modules in P3-P9).
- The Atlas persona overlay shape is now stable (`[workflow]` namespace per spec §7.1, with universal-glob opt-in in `persistent_facts`). P2.2+ skills follow the same pattern.
- QG-M2 is only partially satisfied by P2.1 (H1 threat model + H5 onboarding implications); full satisfaction requires P2.2+ workflows (design-multi-tenant-testing, design-modular-monolith, design-tenant-onboarding).

## Alternatives Considered

- **One large P2 plan covering all 16 workflows** — rejected. ~400 tasks would exceed any reasonable single-plan execution discipline; review cadence collapses; merge conflicts compound.
- **Split by capability area (foundation / lifecycle / FinOps / migration)** — rejected. Would leave activation mechanism unverified for too long; capability splits don't align with the dependency graph (foundation gates everything).
- **MVP slice without Plan C ratification** — rejected. Plan C is the only end-to-end verification that LLMs actually load project-context.md at activation; deferring it would mean P2.2+ work could compound on a broken activation contract.
