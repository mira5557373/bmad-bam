## Context

BAM v6's activation mechanism depends on BMAD v6.4.0+'s universal-glob pattern. Wave 0 was designed to empirically test whether this works in our target BMAD install and select Plan A/B/C accordingly.

## Decision

Selected Plan: **A**.

The headless smoke test (`tests/wave-0/run-smoke-test.sh`) ran against BMAD v6.6.0 (submodule `e36f219c`) and confirmed:
- The literal universal-glob string `file:{project-root}/**/project-context.md` survives BMAD's three-layer customize merge into a core skill's resolved `agent.persistent_facts`.
- The sentinel `_bmad/platform/project-context.md` (generated by `src-v6/bmad-bam-platform/scripts/post-install.sh`) is present at a `**`-matching path with a fresh `BAM_LOAD_VERIFY_<uuid>` token.

Exit code 0 with `plan=A` persisted to `_bmad/bam/family.json` inside the ephemeral test fixture.

The runner does NOT verify the LLM-side `file:` expansion at activation; that contract lives in 30 BMAD SKILL.md prompts and is by-design untestable headlessly. One-time manual Plan C verification with a live agent is recommended before P2 acceptance.

## Consequences

- P2 (bmad-bam-platform full module) inherits Plan A and does NOT need install-time overlay code in its post-install hook.
- All subsequent BAM modules use the same activation mechanism; each must include `persistent_facts = ["file:{project-root}/**/project-context.md", ...]` in its own `customize.toml` (per Task 0 risk #2 — the universal-glob is opt-in per skill, not a global hook).
- `_bmad/bam/family.json` is the canonical record of Plan A selection; P2+ reads `plan` first and adapts behavior accordingly.
- BAM pre-install gates must enforce Python 3.11+ (resolver dependency).
- BMAD version floor stays at >=6.4.0; the test was conducted at 6.6.0 with no degradation expected for the 6.4.x line.

## Alternatives Considered

- **Plan A (universal-glob)** — selected. Invisible to user; no install-time overlay needed in BAM modules.
- **Plan B (explicit user-tier overlay)** — viable fallback. Would require BAM post-install to write `_bmad/custom/<skill>.toml` overrides per affected core skill. Headless test confirmed Plan B also works (not exercised because Plan A passed).
- **Plan C (manual LLM verification)** — kept documented for completeness. Required if a future BMAD release breaks universal-glob in customize.toml merge.

## Migration if plan changes later

If a future BMAD upgrade breaks Plan A's resolver-side string-presence guarantee, run `bmad-bam-smoke-test` again. It will re-evaluate Plan A/B/C and update `family.json`. A new ADR supersedes this one. The `bmad-bam-smoke-test` skill is preserved in `bmad-bam-platform` precisely for this kind of recurring re-validation.
